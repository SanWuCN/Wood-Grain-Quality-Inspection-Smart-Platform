## 1. 现在这一页是什么

原来的 `/knowledge` 是一个「上传 → 更新向量库 → 可视化」的实验工具页：
上传占据一整列、资料与向量挤在一屏、说明文字解释「不连接后端 / 不上传服务器」。
改造后它是一个面向技术人员的**数据与知识中心**，围绕三个问题组织：

1. 平台积累了哪些资料、来自哪里、关联哪个项目或设备？
2. 哪些资料已经进入 RAG 索引，哪些仍在更新或发生异常？
3. 一条检索证据如何追溯到原始资料、构件、工单和历史记录？

结构是「两层数据、四个页签、一套状态」：

| 页签 | 定位 | 首屏内容 |
|---|---|---|
| 总览 | 默认首页 | 六项指标；左栏「数据资产库 + RAG 索引库」（等高），右栏「资产关系 + 更新任务」 |
| 数据资产 | 管理资料 | 分类侧栏 184px + 资产表格、高级筛选折叠、批量更新 |
| RAG 索引 | 运维检索层 | 服务状态卡、覆盖分布、更新任务与阶段、版本记录、索引配置 |
| 检索验证 | 核验知识可用性 | 检索栏、左侧结果 40% / 右侧证据详情 60% |

总览的高度关系是刻意对齐的：**右栏两卡之和 = 左栏两卡之和 = 主体高度**
（1920×1080 实测：左栏 349 + 349 = 698，右栏关系图 525 + 更新任务 172 = 697）。
「更新任务」不再独占一整行，而是并到右栏底部，行内只放摘要
（状态 / 类型与来源 / 版本与计数 / 时间），阶段明细、逐项结果与错误码点开
「任务详情」抽屉看。这样省下的纵向空间全部还给三张主卡。

指标行严格保持 PRD §7.2 的**六项**（资产总量 / 索引覆盖率 / 有效分块 / 向量条目 / 待更新 / 更新异常）。
两层数据的关系不另占指标位，而是写成指标行正下方的一句话：
「共 167,110 项 · 其中 1,500 项可展开明细（有文件名、版本与分块），其余 165,610 项为历史归档的规模样本，只参与统计」。
放在这里是因为看到「资产总量 16.7 万」的人下一步就会去列表里翻；
不先说清「只有一部分能点开」，列表页的「共 X 项 · 其中 Y 项可展开明细」会被当成漏数据。

资产规模。这里有一条必须讲清楚的口径 —— **两层数据**：

| 层 | 是什么 | 参与什么 |
|---|---|---|
| **可展开明细**（1,500 项） | 真的生成了记录：有文件名、版本、来源、分块与索引成员 | 列表、详情、图谱节点、检索、覆盖率 |
| **规模样本**（165,610 项） | 平台里真实存在、但演示库不逐条生成的历史归档计数 | 只参与「资产总量」等统计 |

演示库不会把十六万条记录逐条写进库：没人会翻到第 40,000 条，逐条入库也会让首次启动慢到不可用。
但**规模不能因此缩水** —— 现场照片五万余张、巡检视频一万余条、文档八千余份，
这是古建巡检干几年之后的真实量级，所以它作为计数落库（`knowledge_scale` 表），
指标从「明细 + 规模」两个来源复算，界面在每个主类和列表顶部同时标出两者。

| 主类 | 平台总量 | 可展开明细 | 纳入 | 覆盖 | 待更新 | 异常 | 未纳入 | 有效分块 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 文档报告 | 8,210 | 300 | 300 | 274 | 20 | 6 | 0 | 11,400 |
| 现场照片 | 54,160 | 240 | 120 | 112 | 4 | 4 | 120 | 240 |
| 巡检视频 | 10,420 | 120 | 48 | 40 | 4 | 4 | 72 | 384 |
| 扫描数据 | 24,300 | 120 | 0 | 0 | 0 | 0 | 120 | 0 |
| 高斯场景 | 3,860 | 60 | 0 | 0 | 0 | 0 | 60 | 0 |
| 建模与建图 | 6,450 | 96 | 60 | 54 | 4 | 2 | 36 | 180 |
| 点云数据 | 18,740 | 96 | 0 | 0 | 0 | 0 | 96 | 0 |
| 模型权重 | 2,310 | 60 | 0 | 0 | 0 | 0 | 60 | 0 |
| 音频记录 | 15,920 | 90 | 48 | 42 | 2 | 4 | 42 | 192 |

| **合计** | **167,110** | **1,500** | **870** | **802** | **44** | **24** | **630** | **18,000** |

主类比 PRD 的六类扩到**十二类**：新增扫描仪原始数据、高斯泼溅场景（.sog/.ply/.spz）、
建模与建图产物（.obj/.fbx/.glb/.dwg/.ifc）、点云、模型权重（.pt/.onnx/.engine）、
音频记录。它们必须是独立主类：纳不纳入索引的判定不同（二进制产物没有可检索文本），
统计口径也不同（点云按点数、视频与音频按时长、权重按参数量）。

文档内部另有九类业务分类，其中三类是专业题材：

| 题材 | 正文写的是什么 | 检索它能回答什么 |
|---|---|---|
| 修缮工艺 | 适用范围、材料要求、施工工序、质量控制、成品保护、验收要点 | 这类病害按什么工法修、每层做多厚、允许偏差多少 |
| 政策法规 | 消防配置、日常保养、报批流程、虫害防治、防水排水、工程档案（**六份不同主题，各写各的**） | 依据哪条要求、要报哪一级批、档案存多久 |
| 保护规划 | 保护区划、本体保护措施（数值随建筑与构件变化） | 保护范围多少米、控高多少、瞬时承载量多少 |

**文件名按各类型的真实习惯生成，不是清一色中文**（下面每一条都是从生成的 1,500 条里取的真实样本）：

| 主类 | 实际生成的命名样态 |
|---|---|
| 现场照片 | `DJI_20260909122448_0024.PNG`、`IMG_002401.JPG`、`SH-2026-101_柱脚渗水_4.PNG` |
| 扫描数据 | `FARO03_20260518_112341.PCD`、`ZEB02_20260518_100214.PLY`、`scan_scan-scan-02-0001_0001.PTS` |
| 点云数据 | `cloud_pc-0031_0031.PLY`、`merged_20260909_月台.PCD`、`SH-2026_20260909_047_0147.LAS` |
| 高斯场景 | `月台_gaussian_20260909_0039.SOG`、`splat_gs-0001_v2.PLY` |
| 建模与建图 | `mesh_mdl-0001_0001.DWG`、`SH-2026-105_二层_model.FBX`、`b-zx_20260909_recon.GLB` |
| 模型权重 | `wood_defect_yolov8s_20260814_epoch4_w003.PT`、`segmenter_wt-001_best_w001.ONNX` |
| 音频记录 | `SH-2026_现场录音_0025.MP3`、`REC117_20260909_105307.WAV`、`voice_memo_aud-0003_0003.M4A` |
| 日志批次 | `log-th-2207-0001_session.log`、`woodpulse_20260912_017.JSONL` |
| 文档报告 | `SH-2026-101_二层_report.PDF`、`CRAFT-0300_构件档案.DOCX`、`Mumai_Spec_0102.XLSX` |

实测 **53% 的文件名不含中文**，全库文件名两两不同 —— 生成结束时自检里就有
「文件名不得重复 / 纯英文编号占比不得低于 25%」两条断言，验收脚本 P01 组再断言一次。

这三类专业题材的**正文不共用同一份模板换文件名**：政策法规按主题分篇，保护规划的区划与限值
随建筑取值，每个分块末尾带本文件内的位置标记（`（CRAFT-0300 · 第 1 段）`）。
这样做的直接结果是全库 18,000 个分块**两两不同**（0 个逐字重复）——
PRD §11.2 明确禁止「复制相同片段来制造独立证据数量」，这一条在夹具自检里有断言守着。

### 数据库

`server/storage/db.mjs` 的建表语句扩了 15 张 `knowledge_*` 表
（资产、资产版本、关系、提取内容、分块、向量、索引版本、索引成员、服务指针、任务、任务明细、配置、种子、规模样本、范围）。
`knowledge_assets` 另加 `filename`（原始文件名）与 `materialized`（是否有可展开明细）两列。

**为什么单开表而不复用 `entities`**：知识域是万级行（1,500 条明细 / 18,000 个分块 / 18,000 个向量条目，
外加 165,610 条规模样本计数）。`entities` 表的快照接口会把整场数据读成 JSON 交给四端，
把知识域塞进去会让每次事件驱动的刷新都搬几兆字节。知识域因此走 `/api/knowledge/*` 的分页与聚合查询。

**为什么规模样本用一张 `knowledge_scale` 表而不是页面常量**：「总量」必须是可查询的事实 ——
指标、覆盖分布、资产列表的 `total` 都要从库里读出来并与明细一起复算。
写死在页面里的话，改一个数就要改三处，而且没法在验收脚本里断言它与明细之和等于总量。

## 4. 接口与权限

读取接口（`GET`，`knowledge:read`；检索另需 `knowledge:search`）：

```
/api/knowledge/overview          总览一致快照：metrics（total / materialized / scale）、coverage 每行带 total、scale、scaleNote、materialized 与 covered / pending / error / excluded / chunks、indexStatus、recentAssets、recentJobs、snapshotSeq
/api/knowledge/assets            资产分页与过滤：type、q、objectId、state、source、category、availability、from、to、cursor、limit；返回 items（只有明细层）+ hasMore / nextCursor，外加 total / materialized 两个总数
/api/knowledge/assets/:id        详情：内容、元数据、版本、分块、关系、索引状态、任务结果（只有明细层拿得到 id，规模样本不在 knowledge_assets 里）
/api/knowledge/graph             范围关系子图：view（business|lineage）、focusId、depth、nodeBudget；节点只取有明细的资产
/api/knowledge/indexes           服务指针、版本历史、配置版本、覆盖分布
/api/knowledge/jobs              更新任务列表
/api/knowledge/jobs/:id          任务详情：items、错误码、阶段
/api/knowledge/fixture           夹具报告：资产数、各类数量、分块数、关系数、缺失附件数、错误项
POST /api/knowledge/search       证据检索（读操作，但要 knowledge:search）
```

列表的 `total` 与 `items` **不是同一层**：`total` 数的是筛选范围内的平台规模（含只按主类计数的
规模样本），`items` 一条都不含它们。理由是两个数字各有各的用处 —— 按「现场照片」筛选时列表顶部
写的是「共 54,160 项 · 其中 240 项可展开明细」；只给 `total`，界面只能把五万多项画成一页翻不到底
的列表，只给 `items`，平台规模又被说小成 240。规模样本没有文件名、版本、分块与索引成员，
**不进列表行、不进图谱节点、也不进检索语料**：画上去点开就是死路（没有详情可看、没有内容可搜），
所以 `knowledge:read` 读到的、检索命中的，永远只是明细层那一批。反过来，按关联对象、业务分类、
索引状态、日期或关键词筛选时规模样本没有这些维度，`total` 就如实只数明细层 ——
宁可数字小一点，也不能把不满足条件的规模样本算进去。

写操作全部走现有命令总线（`POST /api/commands`，带 `commandId` 幂等）：

```
asset.register / asset.revise / asset.updateMetadata / asset.setInclusion / asset.delete
knowledge.sync / knowledge.retry / knowledge.cancel / knowledge.activateVersion / knowledge.configure
```

事件：`knowledge.asset.*`、`knowledge.job.started|progress|settled|cancelled`、
`knowledge.index.published|activated`、`knowledge.config.created`。
客户端收到事件后按同一 seq 重拉快照，**不**做「本地总数 +1」。

权限（PRD §13，前后端同时落地）：

| 权限 | 沈 | 史 | 饶 | 马 |
|---|---|---|---|---|
| `knowledge:read` 查看总览、资产与图谱 | ✓ | ✓ | ✓ | ✓ |
| `knowledge:search` 证据检索 | ✓ | ✓ | ✓ | — |
| `knowledge:manage` 导入与维护资产 | ✓ | ✓ | ✓ | — |
| `knowledge:index` 变更规则、启动 / 取消任务、切换索引 | ✓ | ✓ | — | — |

服务端在 `server/services/permissions.mjs` 的 `ACTION_PERMISSION` 与 `ROLE_PERMISSIONS`，
前端在 `src/pages/MumaiDashboard/auth.ts` 的 `Permission` / `ROLE_ACTIONS` / `ROUTE_READ`。
无权限请求返回 403（已验证：马账号请求检索与 `knowledge.sync` 都是 403）。

## 5. 运行与验证

```bash
# 起共享服务（会按需安装 knowledge-demo-v1 夹具并补齐可打开样本）
node server/index.mjs

# 前端开发态
npm run dev            # http://localhost:5173/#/knowledge

# 按当前生成器重装演示夹具（只清空重建 knowledge_* 表，不碰其它会话与业务数据）
node tools/reset-knowledge-fixture.mjs

# 验收：258 项断言（内存库，不动演示库）
node tools/test-knowledge.mjs
node tools/test-knowledge.mjs --verbose

# 仓库既有验证入口
npm run lint
npm run build
```

验收脚本覆盖 PRD §16 的 D01–D13、K01–K13、R01–R07 与演示脚本 S01–S06、
取消（D07）、空数据（D11）、夹具可重复（K13），以及两层资产模型的 P01 组：
每条明细都有非空且两两不同的文件名、纯英文编号占比不低于 25%、十二个主类齐全、
四个二进制主类全部「未纳入」且都有排除原因、总览各分布相加等于总量、图与检索只碰明细层。

**浏览器实测记录**（本机 Chrome + headless CDP）：1920×1080 与 1366×768 两种视口下逐项量过
—— 1920 档内容区（主体）713px：左栏「数据资产库」349 + 「RAG 索引库」349，右栏「资产关系」525 +
「更新任务」172（任务卡是固定高度，样式里也是 172px），两列各自加上卡间距都回到主体高度；
1366 档主体 445px：左栏 217 + 217，右栏图 303 + 任务 130（该档样式里是 130px）。两档都无横向
溢出、无页面级纵向滚动条（`documentElement.scrollHeight` 分别为 1080 / 768），关系图画布在
两种视口下都已建出 canvas（1366 档图高仍不低于 PRD §5.2 的 290px）。
截图存于 `tmp-shot/`（该目录已被 .gitignore 排除）。

一处**值得记下来的坑**：关系图的画布 DOM 用 `useState` 而不是 `useRef` 保存。
数据是异步来的，首帧渲染的是空状态分支，画布 div 那一刻还不存在；
若只挂 ref、初始化 effect 又是空依赖，effect 在挂载时读到 `null`，画布出现后**永远不会再跑一次**
—— 表现是「图例、节点数、关联列表都在，唯独图是空白」。挂到 state 上，画布一出现
effect 就重跑，ECharts 实例才建得起来。这类「数据都在、就是没渲染」的问题不会报错，
只能靠量 canvas 子节点数发现。

另一处**在交付前抓到的真 bug**：资产列表的「总数」与列表本身用的是两套筛选条件
（计数只认项目 / 类型 / 索引状态），按业务分类或来源筛选时列表是对的、总数却是 1248。
现在两处共用同一段 WHERE（`buildAssetWhere`），`hasMore` 也带上同样的条件 ——
否则筛出 57 条之后点「加载更多」会拿到空页。验收脚本里加了六项断言守着这两件事。

## 6. 演示能力（真实执行 vs 场景模拟）

**真实执行：**

- 资产登记、分类、筛选、详情、删除：真实元数据 CRUD，落在 SQLite；
- 支持文件的保存：走既有文件接口，存真实字节与 SHA-256；
- TXT / MD / CSV / JSON / JSONL / LOG：受大小限制的真实读取、解析与分块；
- 24 组可深入展示样本带**真实可打开的文件**（真写盘，`server/assets/knowledge/`）；
- 二进制主类按类型真登记元数据：扫描数据带设备、站点、点数与采集会话，点云带点数与配准标记，
  高斯场景带高斯点数与训练器，权重带框架与参数量，每条都写清排除原因 —— 但**不做文本提取**，
  索引状态恒为「未纳入」（没有可检索文本，就不按文件大小编一段假正文）；
- 索引任务：真的按输入快照逐项处理，真的重新分块、真的写分块与向量记录，
  真的在一个事务里切换服务版本指针并按记录统计；失败项真的不进服务版本；
- 检索：真 2–4 元词项统计 + 余弦，绑定当前服务版本的语料缓存。

**场景模拟（在「数据说明」抽屉里标明）：**

- 向量条目是 `mode=demo` 的逻辑记录，一块一条；`dimensionConfig=768` 只是配置值，
  不代表落盘了稠密向量，也不能拿「条目 × 768 × 4」当磁盘占用；
- 167,110 项里有 **165,610 项是规模样本计数**（`knowledge_scale` 里每个主类一行），**没有逐条生成**：
  没人会翻到第 40,000 条，逐条入库也会让首次启动慢到不可用。它们只参与资产总量、可用性与来源
  分布，不参与覆盖率（分母只算纳入的明细），也不提供列表行、详情、图谱节点与检索命中。
  代价是「平台有多少」与「能点开多少」必须成对出现，所以指标卡、每个主类和列表顶部
  都同时写「共 X 项 · 其中 Y 项可展开明细」，不把五万多张照片硬画成一页列表；
- 检索评分额外叠加对象编号精确匹配与「报告 / 影像」形态偏好，
  阈值与权重都写在配置里（`knowledge_configs.search`）。

**未实现（P1，本 PRD 明确不计入本期）：** 任意 PDF / DOCX / XLSX 的自动文本提取、
真实嵌入 / OCR / ASR、向量数据库、查询评测面板、内容相似视图、批量导出。

## 7. 已知取舍与后续建议

1. **语义检索的召回上限**：本期是词项检索。同义改写（「柱子」↔「柱」）只能靠
   `synonymRevision` 维护的小词表，不宣称语义模型能力。
2. **日志批次的重新分块会改变块数**：服务端按真实文本重切，块数由内容与
   `chunkPolicy` 决定。任务计数里给了 `replacedChunks`，所以「分块变化 = 新块 − 旧块」
   可以逐项核对（PRD §11.2 明确「基线分块数是夹具的验收约束，不是生产规则」）。
3. **切版不修复失败项**：「更新失败」是针对某个目标 revision 的任务结果。
   切到历史版本后这些资产回到「待更新」，失败计数归零 —— 它们本来就还没成功过。
4. **演示调度是手动推进为主**：`createJobRunner` 只在有人启动任务、或页面显式跟踪时
   按 tick 推进，不做常驻后台空转。要演示自动调度需要另外验收（PRD §10.5 的要求）。
5. **图谱的边来自夹具规则与业务字段**，每条边都有 `relationType / evidenceRef / origin`；
   文本相似关系本期不做主视图（PRD §8.4）。
6. **二进制主类没有可检索文本，这是设计而不是缺陷**：扫描 / 高斯 / 点云 / 权重四类本期只登记
   与统计，索引状态会一直是「未纳入」。除非后续单独加一层提取（点云导出构件清单、权重导出
   训练与评估报告之类），否则它们不会进索引 —— 验收里也不要期待这几类的覆盖率上升。
7. **规模层要能逐条浏览，该改的是服务端分页，不是夹具**：本期 `total` 里的 165,610 项只按主类
   计数，`knowledge_scale` 只有类型 / 来源 / 可用性三个维度，所以按关联对象、业务分类、索引状态、
   日期或关键词筛选时，`total` 会如实只数明细层。真实部署若需要逐条浏览这一层，正确做法是在
   平台真实资产表上做服务端分页、按需翻页；在夹具里生成十六万行既解决不了生产数据从哪来的
   问题，又会让首次启动不可用。
