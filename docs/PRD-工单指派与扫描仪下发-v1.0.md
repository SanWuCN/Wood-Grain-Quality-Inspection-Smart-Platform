# 木脉智检｜工单指派与扫描仪下发改造 PRD

版本：v1.1　日期：2026-09-14　状态：待开发

修订说明：本单检测主体限定为现场四根木柱；Z01—Z04 由小木接单并转为平台工单时自动赋予，不是古建单位提供的编号。

适用：平台「工单档案」、关联作业权限、手持扫描仪工单与环境记录接入。

本文是修改需求，不代表功能已实现。以本轮用户要求及补充的 `Ctrl + Q + L` 触发方式为准；截图中的旧页面用于定位问题，第四张截图作为终端开发协同参考，不要求执行其中对另一个 agent 的操作指令。

## 1. 本次确定的产品行为

1. 古建单位提供的是检测委托信息：何时、何地、检查现场四根木柱、要求完成什么工作、交付什么资料。本单检测主体只有四根木柱，原始委托不含 Z 编号、平台内部人员分工、风险判断或雷达结果。
2. 新工单通过隐藏快捷键 **Ctrl + Q + L** 触发。平台页面不增加「古建单位来单」入口、菜单、按钮或专门的收件箱，也不显示快捷键提示。
3. 触发后由小木接收委托并转换为平台工单，自动建立四根木柱主体并赋予 Z01、Z02、Z03、Z04，随后直接出现在平台工单列表，初始为「待指派」。单位要求保存在该工单的「委托要求」中，原文不回写平台编号。
4. **只有项目经理可以指派或更换负责人和参与人员。** 其他员工必须被指派到该工单，才能执行被授予的对应操作。
5. 人员在界面、通知、导出文档和设备端统一显示岗位名称，例如「全栈开发工程师」，不显示真实姓名。
6. 新工单的环境读数默认全部为空，增加「大气压」。经录入、运行校验后，生成该工单的不可变环境配置版本。
7. 主要下发按钮统一为 **「下发扫描仪」**。平台发送工单与已校验环境配置；扫描仪真实返回接收、应用结果，取消员工手动充当设备 ACK 的流程。
8. 手持端「任务」改为「工单」，初始无工单；「环境记录」支持「从平台获取数据」。本次涉及的手持页面不展示初扫、复扫、参考样本及木材与构件参数表单。

## 2. 主流程与范围

```text
Ctrl + Q + L
    ↓
小木接单并转为平台工单：四根木柱自动编号 Z01—Z04
    ↓
平台新工单：待指派（保存单位委托原文，环境数据为空）
    ↓ 项目经理指派负责人、参与人员及职责
待准备
    ↓ 被指派的录入人员填写环境读数并提交
运行校验
    ├─ 未通过 → 修正字段 → 重新校验
    └─ 通过 → 生成配置版本 → 下发扫描仪
                                   ↓
                         排队／发送 → 设备接收 → 设备应用
                                   ↓
                         扫描仪显示工单与环境记录
```

本期不建设古建单位登录门户、外部收文管理或公文审批系统。快捷键是受控的场景触发方式，不表示已经对接真实外部单位系统。平台内部保留来源标识以便区分示例与真实数据，不伪称示例工单来自真实单位。

本期不新增风险评估算法、大气压补偿算法，不将工单下发解释为自动启动扫描，也不更改智能车的运动控制或巡检任务协议。车端 agent 如同时维护手持端，可按第 9 节接入手持业务。

## 3. 新工单触发规则

### 3.1 快捷键

- 平台已登录且页面获得焦点时可触发。为演示便利，已有业务账号均可触发；触发权限不赋予指派或作业权限。
- 操作定义：**按住 Ctrl，先按 Q，再在 1.5 秒内按 L**；按住 Ctrl、Q 后再按 L 也有效。Mac 使用 Control，不替换为 Command。
- 使用按键状态/序列识别，忽略长按产生的 `repeat`；释放 Ctrl、窗口失焦、超时后清除序列。
- 在输入框、文本域、可编辑区域或输入法组字期间不触发。只对匹配的快捷键序列处理默认行为，避免普通按键误建工单。
- 一次完整触发只提交一次创建请求；请求完成前再次触发不重复提交。服务端按触发事件 ID 幂等，同一请求重试返回同一工单。
- 完成后提示「收到新工单 WO-……，待项目经理指派」，工单列表实时刷新并选中新单。若有未保存表单，保留草稿、不强制跳页，通知允许点击查看。
- 刷新、重新登录、其他账号上线后，该工单仍存在。创建失败不显示成功通知；网络恢复后重试原事件 ID。
- 一次触发完成、按键全部释放后再次完整触发，创建另一份新单。单号、来单记录 ID 和时间由服务端生成，不覆盖上一份。

### 3.2 触发后的初始状态

| 对象 | 初始值 |
|---|---|
| 工单状态 | 待指派 |
| 工单编号、平台创建时间 | 服务端生成 |
| 委托单位、地点、计划时间、委托要求 | 来自预置委托样例；原始主体信息为四根木柱，无 Z 编号 |
| 平台检测主体清单 | 小木转换时生成四条木柱记录，自动编号 Z01、Z02、Z03、Z04 |
| 负责人、参与人员、职责 | 未指派；不得沿用上一单 |
| 环境读数、测量时间、仪表编号、测量位置 | 全部为空 |
| 环境配置版本、下发记录、设备应用回执 | 无 |
| 构件检查结果、雷达响应、风险结论 | 未采集／无记录 |
| 采集附件、报告、复巡计划 | 无；原始委托附件单独保留 |

### 3.3 小木转换与主体编号

- 小木负责接单转换的产品流程，服务端执行确定性的编号与落库规则；不让模型自由生成、增减或重排编号。
- 本单必须创建且只创建四条检测主体记录：Z01、Z02、Z03、Z04，类型均为木柱。不增加梁架、配殿、山门等检测主体。
- 编号在平台工单创建时一次生成，不等待人工指派、环境校验或首次下发。创建工单、四条主体记录及转换日志须在同一事务内完成；失败时不留下缺主体的半成品工单。
- `subjectId` 是不可变的内部主体标识，`subjectCode` 是工单内唯一的展示编号。按 `workOrderId + subjectCode` 建立唯一约束；不同工单可各自拥有 Z01—Z04，不能只凭 Z01 关联数据。
- 单位提供四根木柱的明确位置或附件顺序时，按该顺序建立映射并保留来源；如果仅写「四根木柱」，则先创建四条待现场定位的木柱记录，位置为空并标记「待定位」，不得猜测东、西方位或柱型。现场确认位置只更新映射，不重新编号。
- 同一触发事件重试、刷新、跨端查看、人员调整、重复下发均复用已有主体 ID 与编号，不生成 Z05、不重复新增木柱。
- 平台、扫描仪、采集附件和报告统一引用这四条主体记录；采集数据必须关联当前工单下的具体主体 ID。扫描仪只接收平台编号，不在本地另编一套。
- 转换日志记录「小木已创建平台工单，并为四根木柱生成 Z01—Z04」，不意味着小木获得指派负责人或执行检测的权限。

## 4. 古建单位委托应包含哪些内容

### 4.1 字段建议

| 信息 | 必填 | 内容与用途 |
|---|---|---|
| 委托标题 | 是 | 如「关于开展示例寺四根木柱检测工作的委托」 |
| 委托单位 | 是 | 单位全称，不使用平台岗位替代 |
| 委托日期 | 是 | 单位提出委托的日期，与平台创建时间分开 |
| 委托编号／文号 | 否 | 有则保留；没有就留空，不生成虚假的正式文号 |
| 项目／古建名称 | 是 | 例如「示例寺古建筑检测」 |
| 检测地点 | 是 | 行政区、详细地址、院落或建筑位置；经纬度可选 |
| 计划作业时间 | 是 | 开始、结束时间或日期窗口；记录精度及时区，日期不能伪装成精确预约时间 |
| 检测主体及数量 | 是 | 本单为现场四根木柱，数量固定为 4；可附具体位置或示意图，原始委托不提供 Z01—Z04 |
| 委托范围与要求 | 是 | 一段正式书面要求，说明检查范围、资料记录、成果交付要求 |
| 交付内容、期限 | 是 | 例如影像资料、主体位置清单、检测记录、检测报告；未另定期限可明确随作业结束提交 |
| 现场对接信息 | 否 | 单位对接岗位、部门或值班渠道；样例不写真实个人姓名和私人联系方式 |
| 附件 | 否 | 现有建筑平面图、主体清单、单位原始委托文件；必须是实际随单资料 |

本单的检测主体就是现场四根木柱。古建名称、院落或所在建筑仅用于描述地点，不另外建立为检测主体。Z01—Z04 是小木转换后生成的平台编号；不得沿用演示工单中这些编号对应的木材种类、尺寸、修缮历史、缺损描述或雷达结果。

原始委托不设内部负责人、员工分工、来源风险、风险等级、雷达响应、诊断结论、配置版本、算法版本、复巡计划等字段。若单位原件确实附带既有问题描述，作为原件资料保留，不转换成本次检测结论。

## 5. 平台工单页面调整

### 5.1 信息结构

保留「工单档案」导航。左侧使用窄工单列表，右侧为详情；列表建议占 20%—24%，且提供「待指派／进行中／已归档」筛选和单号搜索。

详情从上到下：

1. **工单摘要**：编号、标题、状态、计划作业时间、地点、平台创建时间、负责人岗位。操作按钮随当前账号和状态变化。
2. **委托要求与检测主体**：正式要求正文、Z01—Z04 四根木柱清单、原始附件；原文与平台编号清单分开呈现，长正文可展开。
3. **负责人及参与人员**：负责人、各参与岗位和职责；仅项目经理显示可操作的「指派人员／调整指派」。
4. **环境记录与配置校验**：四项读数、测量信息、录入与校验操作。
5. **扫描仪下发**：目标扫描仪、待下发版本、当前设备版本、下发按钮、实际设备回执。
6. **作业记录与成果**：实际产生的构件记录、数据附件、报告、操作日志；新工单为空态。

原「来源风险」不放在新单摘要；之后确有检测结果时在作业成果中关联。原先默认出现的构件缺损描述、雷达 0.87、模拟附件不灌入新单。旧历史工单照常保留，不删除其实际历史内容。

### 5.2 操作与文案

| 当前表述／行为 | 修改后 |
|---|---|
| 以「生成工单」按钮承接单位来单 | 此来单场景由隐藏快捷键触发；不增加来单按钮 |
| 责任部门里显示个人姓名 | 「负责人：全栈开发工程师」等岗位称谓；单位与负责人分字段 |
| 全栈接收并返回 ack／等待全栈接收 | 「下发扫描仪」／「等待扫描仪接收」 |
| 员工点接收后直接显示设备已确认 | 仅设备真实执行回执可显示「扫描仪已应用」 |
| 环境读数默认 26.4、78、1.2 | 显示「—」和「待录入」，输入框为空 |
| 将 SensorTag 作为独立业务主体 | 扫描仪内置读数属于「实时数据」，设备技术型号仅在详情中展示 |

现有「生成工单／确认草稿」如仍用于内部主动建单，可保留原用途，但不作为本次快捷键入口，也不得绕过本期的指派权限和空环境数据规则。顶部「暂停／归档」只在适用状态显示可用。

## 6. 人员指派和权限

### 6.1 指派方式

- 项目经理选择一名工单负责人，再选择参与账号及职责，一次提交生效。负责人可以同时承担具体职责，但「负责人」身份不自动获得所有专业操作权限。
- 候选项按岗位显示：项目经理、人工智能架构师、全栈开发工程师、具身智能工程师。同岗位多个账号使用「全栈开发工程师 · 01」等非实名编号区分。
- 内部使用不可变 `accountId` 绑定实际账号；不得用岗位文字当唯一身份，也不能把同岗位所有账号自动授权。
- 建议默认职责：全栈开发工程师承担环境录入、扫描仪下发和采集上传；具身智能工程师承担建图巡检；人工智能架构师承担算法及成果审核。项目经理在角色能力范围内选择职责。
- 未指派员工可以在已有项目读取权限内查看工单摘要，页面提示「尚未指派到此工单」；不获得该工单写权限。敏感附件仍按已有项目可见范围控制。

### 6.2 权限矩阵

下表定义本期新增流程的默认权限；项目经理的流程管理权限不等于自动取得所有专业设备操作权限。

| 动作 | 项目经理 | 已指派、且具备对应职责的员工 | 未指派员工 |
|---|---|---|---|
| 指派／更换负责人、参与人员、职责 | 允许 | 禁止 | 禁止 |
| 查看工单 | 按项目范围 | 允许 | 按已有只读范围 |
| 录入、修改、提交环境草稿 | 允许 | 环境录入职责允许 | 禁止 |
| 运行环境校验，生成配置版本 | 允许 | 本期禁止 | 禁止 |
| 选择目标扫描仪、下发已校验包 | 允许 | 扫描仪下发职责允许 | 禁止 |
| 采集上传、建图、成果提交 | 按自身角色及该单职责 | 仅允许被指派的对应内容 | 禁止 |
| 暂停、恢复、验收、归档工单 | 允许 | 本期禁止 | 禁止 |
| 写入扫描仪接收／应用结果 | 禁止人为代写 | 禁止人为代写 | 禁止；仅设备身份可回执 |

服务端对每次操作同时验证：登录身份、项目访问范围、角色能力、当前工单指派、实体归属、工单状态、版本条件。仅隐藏按钮不算实现权限。

人工智能架构师、管理员或小木智能体不能因为现有「全权限」集合而获得指派权；智能体调用必须沿用实际操作者身份，不得代替项目经理完成指派。

### 6.3 调整指派与并发

- 指派记录包含负责人账号、参与账号、职责、指派版本、操作者、时间；界面及导出只显示岗位和非实名编号。
- 调整指派后旧人员立即失去后续写权限；历史记录保持原作者归属。
- 已排队但未执行的旧指派版本下发包失效，必须基于新指派重新生成。设备已应用的旧包保留历史，标记「人员信息待更新」。
- 正在采集时不因换人自动删除数据或强行停止设备；已有批次可完成封存及回传，下一次新作业须取得有效版本。设备回传凭设备身份及批次绑定校验，不能借此恢复旧员工页面写权限。
- 使用 `expectedRevision` 防止两名经理或多端覆盖；冲突返回 409 并提示刷新。

## 7. 环境记录与运行校验

### 7.1 字段和空值

| 字段 | 单位／类型 | 新单默认 | 校验要求 |
|---|---|---|---|
| 温度 `airTempC` | ℃，数值 | null | 必填、有限数值、处于登记仪表量程内 |
| 相对湿度 `relativeHumidityPct` | %RH，数值 | null | 必填、有限数值、0—100 |
| 风速 `windSpeedMs` | m/s，数值 | null | 必填、有限数值、≥0，并符合登记仪表量程 |
| 大气压 `atmosphericPressureHpa` | hPa，数值 | null | 必填、有限数值、>0，并符合登记仪表量程 |
| 测量时间 `measuredAt` | 带时区时间 | null | 必填，不得晚于服务端当前时间超过允许时钟误差；建议误差上限 60 秒 |
| 测量位置 `position` | 文本 | 空 | 必填，属于当前工单地点／测区 |
| 仪表信息 `instruments` | 各参数仪表编号、量程、来源 | 空 | 必填；支持多台仪表，不强迫温湿度、风速、气压共用一个编号 |
| 录入人、提交时间 | 系统字段 | 无 | 服务端生成；录入人按岗位展示 |

风速为 0 是有效的静风记录，不等于缺失。空字符串、空白、null、undefined 必须先判空，再进行数值转换；禁止 `Number(null)`、`Number('')` 被当作有效的 0。量程来自仪表配置，不偷偷回填演示仪表编号或量程。

大气压表示现场实测气压，不默认填写 1013.25 hPa，不把海平面修正气压无说明地混入。允许输入 Pa 或 kPa 时必须显式选单位，转换后统一存 hPa，并保留原始值与单位；1 hPa = 100 Pa，1 kPa = 10 hPa。

### 7.2 录入与传感器数据

- 「录入读数」打开空表单，可以保存未完成草稿；只有完整数据才能提交并通过校验。
- 提供可选的「引用实时读数」：展示可用参数、采样时间、来源，经录入人确认后复制为本单记录。设备持续上报不能自动覆盖已录入或已校验值。
- 设备未提供或已失效的参数保持空。扫描仪没有风速数据时，风速由外部仪表人工补录，不能补 0。湿度等通道异常时同理。
- 推荐仅允许引用最近 10 秒内有效读数；此阈值作为可配置产品规则，不改变设备传感器采样频率。人工历史读数保留真实测量时间，不能伪造为当前采样。
- 切换工单按 `workOrderId` 读取草稿、版本和历史；禁止取共享会话的「最新环境记录」直接填到另一张工单。

### 7.3 校验和版本

1. 员工录入后提交，项目经理点击「运行校验」。前端提示字段错误，服务端再次执行同一规则。
2. 不通过时逐项提示，保留草稿，不生成有效配置版本，不允许下发。
3. 通过后生成不可变 `configVersion`，绑定工单、草稿版本、输入值、来源、校验结果、方法版本、操作者、时间。
4. 通过校验只表示配置有效且可下发，不代表扫描仪已经收到。
5. 修改任一环境值或测量元信息后产生新草稿，标记「需重新校验」。本期不允许借旧版本下发绕过当前未校验修改；扫描仪原已应用版本可继续显示为历史当前值。
6. 版本保存后不可原地改写；新版下发成功后才更新目标扫描仪的已应用版本。
7. 大气压本期用于记录、追溯和下发，不新增压力修正公式。现有 HH 平衡含水率估计沿用已有方法边界，只使用支持的温湿度输入，不冒充木材内部实测含水率。风速与大气压不擅自代入。湿度边界等导致估算不可用时单独显示「无法估算」，不伪造数值。

## 8. 工单和下发状态

### 8.1 工单状态

```text
待指派 → 待准备 → 待作业 → 作业中 → 待验收 → 已归档
                     ↕         ↕
                         已暂停
```

- 待准备：已指派，环境或设备下发尚未完成。
- 待作业：扫描仪已应用有效工单与配置包；并不代表自动开始采集。
- 作业中：收到实际作业开始事件，或由经理按已接入的业务流程开始；不能以命令已发送冒充实际采集开始。
- 暂停保存原状态，恢复返回原阶段；暂停和归档阻止新的下发与采集启动。晚到回执可记录历史，不得让暂停／归档工单恢复执行。
- 下发失败不删除工单、不清空读数，也不把工单直接标成检测失败。

### 8.2 下发状态独立展示

| 状态 | 进入条件 | 页面文案 |
|---|---|---|
| 未下发 | 无下发记录 | 待下发 |
| queued | 包和命令持久化，设备未连接 | 等待扫描仪上线 |
| sent | 已发到设备通道 | 等待扫描仪接收 |
| accepted | 设备接受命令 | 扫描仪已接收，正在应用 |
| executed | 设备验包、持久化并成功应用 | 扫描仪已应用 |
| failed | 设备明确失败 | 下发失败，显示可理解的原因 |
| expired | 超过命令有效期且未执行 | 下发超时，可重新下发 |
| superseded | 工单／指派／配置版本已更新或被撤销 | 已失效，需下发最新版本 |

「下发扫描仪」前置条件：已指派、权限有效、当前环境版本校验通过、目标设备已绑定且支持协议、工单可操作。设备离线时允许明确排队；沿用现有默认 5 分钟命令有效期，过期不自动补发。

超时重试创建新的下发尝试、保留旧记录；网络重传复用原幂等键。重复点击同一有效下发不产生多条业务命令。设备回执迟到或乱序时，不把 executed 回退为 accepted；旧版本回执不能更新新版本的「已应用」状态。

## 9. 平台与手持扫描仪接口约定

### 9.1 现有能力与本期新增边界

现有代码已经有设备注册、心跳、WebSocket、命令下发、三态回执基础，但本期的工单包语义和原子应用仍需开发。以下新增接口是本 PRD 的拟定契约，不声称当前可调用。

| 接口 | 现状／本期处理 |
|---|---|
| `POST /api/devices/register` | 复用；增加业务包能力声明，例如 `workOrderBundleV1` |
| `WS /ws/devices/{id}` | 复用现有设备通道和消息外壳 |
| `POST /api/devices/{id}/commands` | 复用网关；增加工单归属、指派、配置有效性校验，禁止客户端任意拼包绕过业务校验 |
| `POST /api/device-events/batch` | 复用 `command.accepted / command.executed / command.failed` 事件 |
| `POST /api/configs/{version}/ack` | 现有现场调参回写用途保留；不得直接当成本期整包应用成功 |
| `POST /api/work-orders/trigger` | 新增；接收快捷键事件 ID，由服务端生成示例委托及工单 |
| `GET /api/work-orders`、`GET /api/work-orders/{id}` | 新增或对现有工单读取能力补齐，返回服务器持久化数据 |
| `PUT /api/work-orders/{id}/assignment` | 新增；仅项目经理，携带 `expectedRevision` |
| `PUT /api/work-orders/{id}/environment-draft` | 新增；保存本单环境草稿，未填参数为 null |

| `GET /api/devices/{id}/work-order-bundles/pending` | 新增；设备主动拉取尚有效的、明确下发给自己的包，不返回任意全局最新工单 |

### 9.2 一次下发，一个业务包

本期采用**工单与环境配置整包下发**，避免设备拿到新工单配旧环境。主动作使用已有 `assign_task` 命令，其 `args` 增加 `bundleId`、包 URL 和 SHA-256。不再并发发送互不关联的工单、环境命令；旧 `apply_config` 仍服务于原有用途，本期不得借它绕过整包校验。

包的 HTTP 响应体为固化后的 UTF-8 JSON 字节；摘要计算这份响应体，不包含摘要字段本身。命令携带摘要，设备对下载字节验签摘要后解析。URL 不带明文凭据，下载使用设备认证。

### 9.3 推送、主动获取与回执

1. 平台提交下发：在事务内保存包、下发记录及网关命令。沿用现有消息外壳中的 `schemaVersion/type/deviceId/bootId/demoSessionId/messageId/seq/sentAt`，业务版本放在包里，不替换网关版本。
2. 扫描仪收到 `assign_task`，或用户点击「从平台获取数据」主动查询 pending。两种方式处理同一包及同一命令 ID，不生成两份工单。
3. pending 无有效包：显示「暂无平台下发数据」，保留当前已应用记录；未下发的草稿、未校验版本不对设备开放。重复拉取可返回当前有效版本并标明无需更新。
4. 设备检查目标设备、工单／指派版本、有效期、摘要、字段及协议能力，在本地事务中同时保存工单和环境配置。任何一步失败，保留上一个有效版本。
5. `command.accepted` 仅表示已接受命令；完成持久化与实际应用后才上报 `command.executed`。失败报 `command.failed` 和原因。
6. 执行结果至少包含 `commandId`、`bundleId`、`workOrderId`、`workOrderRevision`、`assignmentRevision`、`configVersion`、`appliedAt`；事件外壳携带认证设备 ID 和唯一 `messageId`。
7. 服务端验证设备身份与命令目标一致、结果版本与包一致、命令确实已下发，再推进状态。其他设备、普通员工或伪造旧回执不得更新当前包。
8. 断网时设备保留未发送回执，恢复后幂等补传；平台在收到回执前只显示等待确认，不推断成功。已应用包重复送达只补回执，不重复激活或启动采集。
9. 存在多个待处理包时，按工单和版本分组；同单只允许最新有效版本应用。扫描仪已有进行中作业时，新工单暂存待办，不自动切走当前采集界面；此时保持 accepted，附带「等待切换工单」原因，不提前上报 executed。操作者在有效期内显式选择并完成应用后才回 executed，结果声明 `activationState: active`。超过有效期仍未激活的包不得启用，需平台重新下发。
