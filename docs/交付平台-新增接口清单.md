## 1 通用约定

```
Base:  http://<平台主机局域网IP>:8000
认证:  X-Device-Token: <device_token>
       X-Device-Id:    <device_id>
格式:  application/json（文件分片除外，见 §3.6）
成功:  任意 HTTP 2xx。业务结果放在响应体里，**非 2xx 一律视为失败并退避重试**
```

⚠️ **平台必须监听局域网**（不能只绑 `127.0.0.1`），否则 Pi 连不上。平台自带的
`start-lan.sh` 就是干这个的。

⚠️ **两台设备不能共用 `deviceId`**：平台按 `deviceId` 建台账，重号会互相顶掉
对方的 WebSocket 连接。

## 2 批次 A · 必须（做完即在线）

### A1 `POST /api/devices/register` —— 开机握手

**请求**

```jsonc
{
  "schemaVersion": "1.0",
  "deviceId": "handheld-02",
  "bootId": "boot-019dc7019170",      // 每次进程启动都不同，平台用它区分"重启"与"掉线"
  "appVersion": "2.0.0-demo",
  "adapterVersion": "2.0.0-demo",
  "modelVersion": "DEMO-M02",
  "operatorId": "rao",
  "host": { "hostname": "SANWU", "machine": "aarch64",
            "platform": "Linux-6.12…", "python": "3.13.5" },
  "startedAt": "2026-09-14T12:55:38Z",
  "capabilities": {
    "camera": "live", "radar": "replay", "imu": "unavailable",
    "battery": "unavailable", "telemetry": "live",
    "gpu": "unavailable", "preview": "live"
  }
}
```

**响应**（200）

```jsonc
{
  "ok": true,
  "deviceId": "handheld-02",
  "registeredAt": "2026-09-14T12:55:38.9Z",
  "platformTime": "2026-09-14T12:55:38Z",   // ★ 必须给，见下
  "heartbeatIntervalMs": 5000,               // 可选，覆盖终端默认 5s
  "offlineAfterMs": 15000,                   // 可选，覆盖终端默认 15s
  "configVersion": "CFG-02",                 // 可选
  "demoSessionId": "demo-01",                // 可选
  "pendingCommandCount": 0                   // 可选
}
```

**平台侧要做的**

- [ ] 按 `deviceId` 建/更新设备台账，记录 `bootId`、`lastSeenAt`、`capabilities`、版本号
- [ ] **返回 `platformTime`**：终端拿它和本机时间比对，算出"对工单时间基准"的时钟偏差，
      报在设备数据的 `readings.clock` 里。**没有这个字段，那一项终端就不上报**
      （终端不会填 0 假装同步）
- [ ] **幂等**：终端重连时会再握一次手，第二次不能当新设备

**校验**：`schemaVersion` 主版本不是 `1` 时终端拒收（当前只认 `1.x`）。

### A2 `WS /ws/devices/{deviceId}` —— 设备通道

**这是"在线/离线"的唯一判据。** 终端连上即 `online`；连不上按 1→2→4→8→20 秒退避重连。

```
ws://<平台主机>:8000/ws/devices/handheld-02?deviceToken=<令牌>&demoSessionId=demo-01&bootId=boot-…&appVersion=2.0.0-demo
```

⚠️ **不要复用平台现有的 `/ws`**。那个是**浏览器事件广播**（客户端带 `?sessionId=&afterSeq=`，
服务端单向推），和这条不是同一个通道：设备通道是**双向**的（上行心跳/遥测/事件，
下行命令），路径也不同。

**平台侧要做的**

- [ ] 新起一个 `WebSocketServer({ server, path: "/ws/devices" })`，或让现有 hub 支持第二个 path
- [ ] 升级时校验 `deviceToken`
- [ ] 连接建立后**推一条欢迎消息**（终端会记一条"平台握手完成"）：

```jsonc
{
  "kind": "hello",                       // 终端认 hello / welcome
  "type": "device.welcome",
  "schemaVersion": "1.0",
  "deviceId": "handheld-02",
  "bootId": "boot-…",
  "seq": 1,
  "sentAt": "2026-09-14T12:55:38Z",
  "payload": {
    "platformConfig": { "heartbeatIntervalMs": 5000, "offlineAfterMs": 15000 },
    "pendingCommandCount": 0
  }
}
```

- [ ] 维护 `deviceId → socket` 映射，用于下发命令（§4.1）
- [ ] 断线时清理映射并更新台账 `lastSeenAt`

### A3 心跳与在线判定

终端每 5 秒（或 `heartbeatIntervalMs`）发一条：

```jsonc
{
  "type": "device.health",
  "deviceId": "handheld-02",
  "bootId": "boot-…",
  "seq": 128,
  "sentAt": "2026-09-14T12:56:02Z",
  "payload": {
    "schemaVersion": "1.0",
    "deviceId": "handheld-02",
    "bootId": "boot-…",
    "heartbeat": true,
    "platformLatencyMs": 9.7
  }
}
```

**平台侧要做的**

- [ ] 收到 `device.health` 就更新 `lastSeenAt`（**不需要专门回一条心跳响应**）
- [ ] **但必须回点东西**：终端按"15 秒内有没有收到平台任何消息"判定 `degraded`。
      平台如果只收不回，终端会一直显示"平台响应延迟"
- [ ] 平台自己的离线判定：`lastSeenAt` 超过 `offlineAfterMs` 就在平台 UI 标离线
      （终端和平台各算一份，不冲突）

终端侧状态判定表：

| 条件 | 终端状态 |
|---|---|
| WS 连着，15s 内收到过平台消息 | `online` |
| 10s 没收到平台消息 | `degraded`（响应延迟） |
| 15s 没收到平台消息 | `degraded`（长时间无消息） |
| WS 断开 | `connecting` → 退避重连 → `offline` |

### A4 `POST /api/device-events/batch` —— 关键事件与命令回执

⚠️ **这条最容易做错，三条硬要求全部在联调时踩过。**

**请求**

```jsonc
{ "events": [ /* 信封数组，见 §4.2 */ ] }
```

**响应**（200）

```jsonc
{
  "accepted":   ["msg-111", "msg-112"],   // ★ messageId 数组，不是计数！
  "duplicated": ["msg-113"],              // ★ 同上
  "rejected": [
    { "messageId": "msg-114", "reason": "未知事件类型",
      "code": "unknown_type", "retryable": false }
  ]
}
```

**三条硬要求**

1. **`accepted` / `duplicated` 必须是 messageId 的字符串数组**。
   返回计数（`{"accepted": 2}`）终端会解析失败，表现是**事件永远在重传**。
2. **每个收到的 messageId 最终必须出现在三个数组之一**。
   静默丢弃 = 终端拿不到确认 = 按退避无限重推同一批。这是实测到过的现象。
3. `rejected` 里 **`retryable: false`** → 终端出队不再重试（未知类型、版本不符、deviceId 不符）；
   **`retryable: true` 或缺省** → 终端保留并退避重试（平台过载、队列满）。

**无论平台内部怎么处理，HTTP 都返回 200**，业务结果放 body。

**平台侧要做的**

- [ ] 加表 `device_events(message_id PRIMARY KEY, device_id, type, payload, received_at)`
- [ ] 按 `message_id` 去重：已存在 → 进 `duplicated`，不重复入库
- [ ] 未知 `type` → 进 `rejected` + `retryable: false`（**不要静默丢**）
- [ ] 建议自设批量上限（如 500 条/批），超了返回 413 让终端拆小；**别静默截断**

## 3 批次 B · 数据交付

### B1～B3 文件分片上传（三步）

**为什么分片**：批次里 `frames.csv` 有几 MB，一次 POST 全网断一次就全废。
分片后平台按 `offset` 记进度，重连从 `receivedOffset` 继续。

#### B1 `POST /api/files/uploads` —— 创建

```jsonc
{ "name": "frames.csv", "size": 804392,
  "sha256": "<64位十六进制>",          // ★ 不能为空
  "batchId": "scan-Z04-002", "role": "frames",
  "schemaVersion": "1.0" }
→ 201 { "uploadId": "up-79b373b44992", "receivedOffset": 0 }
```

⚠️ **`sha256` 为空会被平台按 422 拒掉**，表现是"最后一个文件永远传不上去"。
终端上传前一定会在本机算一遍，但平台侧也要挡住空摘要。

⚠️ **断点续传**：若 `batchId + name` 的上传单已存在，平台应**返回同一个 `uploadId`
并带上 `receivedOffset`**，终端会从那里继续。**每次新建就永远续不上。**

#### B2 `PUT /api/files/uploads/{uploadId}/chunks` —— 传分片

```
Header: X-Chunk-Offset: 524288
        X-Chunk-Sha256: <这一片的 sha256>
Body:   <application/octet-stream>
→ 200 { "receivedOffset": 1048576 }
```

⚠️ 重复 offset 的分片按**幂等**处理（返回 200，不报错）。

#### B3 `POST /api/files/uploads/{uploadId}/complete` —— 完成

```jsonc
{ "sha256": "<整个文件的摘要>", "size": 804392 }
→ 200 { "ok": true, "sha256": "<平台重算的>", "match": true }
```

⚠️ **平台必须自己重算整文件摘要**并与声明值比对——这是终端"摘要校验"链路的平台侧一半。
`match: false` 时终端会把这个文件标失败。

**`role` 取值**：`frames` / `segments` / `marks` / `marks_csv` / `quality` / `result` /
`config` / `dataset` / `plan` / `events` / `image` / `image_index` / `batch`

### B4 `POST /api/batches` —— 提交批次清单

```jsonc
{ /* manifest */ }
→ 200 { "ok": true, "batchId": "…",
        "received": { "files": 10, "bytes": 804392 }, "missing": [] }
```

**关键字段**：`batchId`、`orderId`、`componentId`、`zoneId`、`configVersion`、
`modelVersion`、`scenarioId`、`datasetHash`、`files[]`

**平台侧要做的**

- [ ] **校验并回显 `datasetHash`**：两端各自算过同一个摘要，只有平台能确认"收到的
      就是终端封存的那一份"
- [ ] `missing` 非空时终端在交付页显示"部分接收"
- [ ] 未知字段**不校验也不丢弃**，原样收下

## 4 批次 C · 展示与交互

### 4.1 下行命令

平台通过 A2 的 WebSocket 推：

```jsonc
{
  "type": "command",          // 终端认 command / device.command / command.* 三种
  "deviceId": "handheld-02",
  "bootId": "boot-…",
  "seq": 3,
  "sentAt": "2026-09-14T12:57:00Z",
  "payload": {
    "commandId": "cmd-2993635511f0",
    "type": "assign_task",
    "expiresAt": "2026-09-14T13:02:00Z",
    "args": { /* 见下 */ }
  }
}
```

**终端支持的命令**（白名单，别的不认）：

| `type` | 作用 |
|---|---|
| `assign_task` | 派发工单（§4.3） |
| `apply_config` | 下发环境配置 |
| `pause_capture` | 请求暂停采集 |
| `request_upload` | 请求上传本批数据 |
| `prepare_update` | 准备更新 |
| `query_status` | 查询状态 |

**终端一定回三条回执之一**（走 A4 的事件通道）：

| 回执 | 含义 |
|---|---|
| `command.accepted` | 已收到、格式合法（**不代表执行了**） |
| `command.executed` | 动作真正做完 |
| `command.failed` | 带 `code` 与 `reason` |

⚠️ **`accepted` ≠ `executed`**，平台 UI 不要把前者显示成"已完成"。
⚠️ `expiresAt` 过期的命令终端拒执并回 `command.failed` / `code = "command_expired"`。
**别下发 `expiresAt` 是过去时间的命令。**

### 4.2 消息信封（所有 WebSocket 消息统一这个壳）

```jsonc
{
  "schemaVersion": "1.0",
  "type": "device.health",
  "deviceId": "handheld-02",
  "bootId": "boot-019dc7019170",
  "demoSessionId": "demo-01",
  "messageId": "msg-7f3a1c2b",     // ★ 幂等键，平台按它去重
  "seq": 128,
  "sentAt": "2026-09-14T12:56:02Z",
  "payload": { }
}
```

终端校验：缺 `type` / `deviceId` / `bootId` / `seq` / `sentAt` 任一即拒收；
`schemaVersion` 主版本不符也拒收。**平台下发的消息请照这个壳写。**

**终端会发的 `type` 全集**

| 分类 | 类型 |
|---|---|
| 设备 | `device.register`、`device.hello`、`device.health`、`device.telemetry`、`device.capabilities`、`device.selfcheck` |
| 采集 | `capture.started`、`capture.paused`、`capture.resumed`、`capture.finished`、`capture.mark_created`、`capture.progress`、`capture.anomaly` |
| 批次 | `batch.finalized`、`batch.upload_started`、`batch.upload_completed` |
| 配置 | `config.received`、`config.applied` |
| 命令 | `command.accepted`、`command.executed`、`command.failed` |
| 更新 | `update.downloaded`、`update.verified`、`update.applied`、`update.failed` |
| 系统 | `system.recovered`、`system.error` |

### 4.3 `assign_task` 的工单数据包（规范）

**终端默认不带任何工单**，刚开机时工单页只显示"等待平台下发工单"。

```jsonc
"args": {
  // ——— 工单页直接显示这九项 ———
  "orderId":     "SH-2026-0918",          // ★ 必填，空则整包拒绝
  "scheduledAt": "2026-09-18 09:00",      // 作业时间
  "site":        "上海市·真如寺·大雄宝殿",  // 地点（也接受 location）
  "createdAt":   "2026-09-15 14:20",      // 创建时间
  "assignee":    "饶工",                   // 负责人员（也接受 owner / operator）
  "department":  "项目经理",               // 责任部门
  "scope":       "山门东侧 Z01",           // 检测范围
  "risk":        "岩层滑移",               // 来源风险
  "rescanPlan":  "未生成",                 // 复扫计划

  // ——— 作业绑定：终端内部用，工单页不显示 ———
  "componentId": "Z04",
  "zoneId":      "Z04-lower",
  "round":       "initial",                // initial | rescan | reference
  "scenarioId":  "initial-anomaly-v1",     // 样例包（本机回放用）
  "configVersion": "CFG-02",
  "modelVersion":  "DEMO-M02",
  "taskRevision":  3                       // 建议每次派单递增
}
```

**平台侧要做的**

- [ ] `orderId` 缺失时**整包拒绝**（终端回 `command.failed` / `code = "missing_order_id"`）。
      终端**没有本地兜底工单** —— 早先给过一套默认值，结果平台只发半个包也能
      "绑定成功"一张假工单，现场分不清屏幕上这单是真是假
- [ ] 时间字段格式建议 `YYYY-MM-DD HH:mm`（本地时间），也接受 ISO8601。
      **不要发 epoch 数字**，那在屏幕上就是一串整数
- [ ] 地点建议"城市·建筑·构件"层级写法，**20 字以内**（那一格宽度有限）
- [ ] 终端会把工单记进本地 `orders` 表，工单页左下「历史工单」列表读它，
      点一行只读预览。**历史不依赖平台在线，重启后仍在**

### 4.4 `GET /api/devices/{deviceId}/environment` —— 拉取环境记录

终端设置页有一个**「从平台获取」**按钮。现场操作者拿仪表读完温湿度风速，
按一下把平台侧登记的那份环境记录取回来填进滑钮。

**为什么是"终端拉"而不是"平台推"**：记录环境是操作者的动作——他读完数才按这一下。
平台推的话，终端不知道什么时候该覆盖他刚看的读数。

```
GET /api/devices/handheld-02/environment
→ 200 {
    "airTempC": 31.5,              // 环境温度 ℃
    "relativeHumidityPct": 78.0,   // 相对湿度 %
    "windSpeedMs": 1.4,            // 风速 m/s
    "airPressureKpa": 100.6,       // 大气压 kPa（可选）
    "instrumentId": "THM-02",      // 仪表编号（可选）
    "position": "四柱区域入口",      // 测量位置（可选）
    "measuredAt": "2026-09-18T09:12:00Z",   // 测量时间（可选）
    "source": "manual-instrument"  // 来源（可选）
  }
```

**平台侧要做的**

- [ ] 落这条路由，从工单/环境记录里取当次工单的环境值返回
- [ ] 字段名也接受下划线写法与常见别名（`temperature` / `humidity` / `wind` / `pressure`），
      终端会依次尝试
- [ ] **只给能给的项**，缺的项沿用终端当前值，**不会被清零**

⚠️ 两条注意：

1. 这一拉**只填滑钮、不直接生效**——操作者还要点「应用参数」。所以平台不需要在这里做版本管理。
2. 它是**"环境记录"，不是"配置版本"**。配置下发仍走 `apply_config`（§4.1）。
   配置是"该用什么参数"，环境记录是"现场量到多少"，两者不要混。

### 4.5 `POST /api/configs/{configVersion}/ack` —— 配置回写

终端有两种写法：

```jsonc
{
  "deviceId": "handheld-02",
  "configVersion": "CFG-02-L3",
  "state": "local-tuned",          // applied = 平台下发后操作者确认；local-tuned = 现场本机调参
  "bootId": "boot-…",
  "appliedAt": "2026-09-14T12:58:11Z",
  "snapshot": { /* 完整配置快照，含 compensation.tuning 全部 14 项参数 */ },
  "diff": [["环境温度", "26.0 ℃", "31.5 ℃"], ["补偿增益", "1.00 ×", "1.08 ×"]]
}
```

**平台侧要做的**

## 7 设备边界（平台展示口径请一并遵守）

接入平台**不会**改变这些，平台 UI 也不要因为"连上了"就改口径：

| 项 | 口径 |
|---|---|
| 毫米波回波 | **没有真实回波**。响应序列全部来自预制样例包，`capabilities.radar` 恒为 `replay` |
| IMU / 姿态 | **没有**。不提供枪体姿态、航向、轨迹 |
| 电池 / 续航 | **没有电量计**。不提供电量，**不要补默认值** |
| 端侧结论 | 批次结果只是"待复核的初筛"；冻结的批次一律不出结论 |
| SoC 温度 | **不是**木材周围环境温度。环境温湿度只来自平台下发的仪表记录 |
| 平衡含水率 | 是**环境先验**，不是木柱内部实测含水率 |
| 风速 | 只作采集稳定性记录，**不代入**含水率模型 |
| 网卡速率 | 是**接口流量**，不是本应用上传速率 |

这些不是"还没做"，是这台设备的真实边界。平台按这个口径显示，两边说的话才一致。

## 8 离线行为（平台不可达时终端怎么表现）

终端是**离线优先**设计的，平台挂了现场照样干活：

| 平台状态 | 终端行为 |
|---|---|
| 完全不可达 | 仍可采集、标记、结束批次；文件进 outbox；1→2→4→…→20 秒退避重连 |
| 上传中断 | 分片续传，从平台报的 `receivedOffset` 接着传 |
| 事件未确认 | 留在本地 outbox 退避重试，重连后补传 |
| 命令下发失败 | 本地任务状态不变；工单绑定是本地事实，不等平台 |

**所以平台恢复后要做的是"接收补传"，不是"重新下发"** ——
终端会把断线期间的事件和文件自己补上来。平台按事件里的 `sentAt` 回放那段时间的状态即可。
