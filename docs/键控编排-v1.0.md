## 1. 现有键位表（逐字对齐实现）

实现位置：`XiaomuDock.tsx` 第 179–208 行的 `onKey`，监听方式 `window.addEventListener("keydown", onKey)`，组件挂载在 `AppShell` 里，因此**每个已登录页面都生效**。

| 键位 | 作用 | 生效条件 | 设计理由 |
| --- | --- | --- | --- |
| **Esc** | 停播报 + 取消未确认的高风险操作 + 收起气泡（走统一 `close()`：`speechSynthesis.cancel()` → 有待确认则 `resolveConfirm(false)` → `setExpanded(false)` → `closeAgent()`） | 仅当 `agent.open \|\| expanded` 为真时处理；两者都为假时**直接 return**（既不 `preventDefault`，也不做任何事） | PRD FR-08 明确要求支持 Esc；Esc 是最常用的"打断"键，且没有输入语义，可以安全地做单键 |
| **Alt+W** | 常驻唤醒 **开/关**：通道状态为 `live` 时 `stop()`，否则 `start()` | 任意页面；不要求气泡可见 | 分组里的"**想说话**"（**W**ake）。开麦/停麦是语音交互的总开关，放在最顺手的位置 |
| **Alt+E** | **展开/收起**气泡面板（`setExpanded` 取反） | 任意页面 | 分组里的"**想看详情**"（**E**xpand）。与点小木形象是同一个动作 |
| **Alt+R** | **重播**最近一轮小木主回答（`latestBotTurn(agent.turns)` → `speak(turn.text)`） | 任意页面；**没有最近一轮回复时无任何动作**（静默忽略，不报错） | 分组里的"**想重播**"（**R**eplay）。与气泡里的「重播（Alt+R）」按钮一一对应 |
| **Alt+M** | **重新开始常驻聆听**（`wakeChannel().start()`） | 任意页面；`start()` 幂等（已是 `live`/`starting` 时直接返回 true） | 分组里的"**想重新说**"（**M**ic）。喊错了、说了一半想重来时的复位动作 |

修饰键规则（照抄实现）：

- 非 Esc 的键统一要求 `event.altKey` 为真，且 `event.ctrlKey`、`event.metaKey` 为假；
- 键名取 `event.key.toLowerCase()`，所以 `Alt+Shift+W` 也会命中 `w`；
- 命中后一律 `event.preventDefault()`；
- **没有**判断 `event.repeat`（长按会连续触发：长按 Alt+W 会反复开/停，长按 Alt+E 会快速翻转）；
- **没有**判断事件源是否是输入框/文本域，也**没有**判断输入法组合态（`isComposing`）；
- **没有**判断 `event.shiftKey`；
- Esc 分支不检查任何修饰键，所以 `Alt+Esc`（甚至 `Ctrl+Esc`，如果被页面收到）也等同于 Esc。

界面上与键位对应的可点控件（保证"键 = 按钮"，不是另造一套语义）：

| 键位 | 对应控件 | 位置 |
| --- | --- | --- |
| Esc | 「×」按钮（提示「关闭（Esc）」） | 气泡标题行最右 |
| Alt+W | 「开启常驻唤醒」/「常驻唤醒：已开」 | 气泡底部；小木助手面板头部「常驻唤醒」按钮是同一个开关 |
| Alt+R | 「重播（Alt+R）」 | 回复底部 |
| Alt+E | 小木形象本体（点击展开/收起） | 右下角 |
| Alt+M | 无对应按钮（等价于重新点一次「开启常驻唤醒」） | — |

## 2. 编排逻辑：按"用户此刻想干什么"分组

键位不是随手挑的，分组依据是**用户当下的意图**，而不是"哪个键还空着"：

| 用户此刻想干什么 | 键 | 为什么是这一类动作 | 助记 |
| --- | --- | --- | --- |
| 想说话 / 不想让它听 | **Alt+W** | 这是语音交互的**总开关**：开麦、停麦都在这一个键上，语义单一，误按的代价只是多听或少听一段，不会动业务 | **W**ake |
| 想让它闭嘴（打断） | **Esc** | 播报中、等待确认中、正在识别的三种情况下，用户最需要的是"立刻停"；Esc 是通用"退出当前动作"的约定，且 PRD 要求 | **Esc**ape |
| 想看详情 | **Alt+E** | 与"点形象展开"同一动作；用户想看回复细节时不用瞄准右下角 | **E**xpand |
| 想重播 | **Alt+R** | 播报只念一次，演示/嘈杂现场常需要再听一遍；重播是**只读**动作，不会重复执行工具（重播只调播报，不重新 `ask()`） | **R**eplay |
| 想重新说 | **Alt+M** | 喊错、说了一半、被环境噪声打断时，需要一个"复位麦克风"的动作；它是纯输入侧动作，不动业务状态 | **M**ic |

这套编排有三个刻意的取舍：

1. **全部动作都在"交互层"，没有一个直接触发业务。** 五个键里没有一个会执行工具、跳页面或改业务状态 —— 高风险操作只能由**语言**触发并经过确认层，键盘不能成为绕过确认的后门。
2. **与气泡里的按钮一一对应。** 用户学会一个键，就等于学会一个按钮；反之亦然。没有"只有键盘才能做到"的能力，也没有"只有鼠标才能做到"的能力（Alt+M 是唯一的例外，它等价于重复点唤醒开关）。
3. **不做组合键的层级结构（没有 leader key、没有 Ctrl+K 面板）。** 五个键各自独立、都可盲按；小木是常驻配角，不应该要求用户先学一套前缀键。

## 3. 为什么不用单键（除 Esc）

单键看起来更省事，但在本平台会立刻坏掉：

1. **会与页面上的输入框抢键。** 平台有大量文本输入（小木助手的提问框、诊断控制台的指令框、知识库检索、工单/文档编辑等）。用户在里面打 `w`、`e`、`r`、`m` 是**输入文字**，不是命令。单键快捷键必须额外做"焦点在输入框时不响应"的判断，而这恰恰是最容易漏、最容易出线上事故的地方（漏一次就是"打字打着打着麦克风关了"）。
2. **会与地图/三维页面的相机操作语义冲突。** 地图与数字孪生页是空间操作场景，`W/A/S/D`、方向键这类按键是这类页面的天然语义。**需要如实说明的是**：在当前仓库代码里，`src/pages/MumaiDashboard/` 下**查不到任何地图键盘控制实现**（全仓 `addEventListener("keydown")` 只有 4 处，见第 4 节；`map/` 目录下没有 `listenToKeyEvents`、没有键盘事件）。所以这一条是**面向后续演进的约束（预防性设计）**，不是当前已发生的冲突。把地图键盘控制留给地图，是小木不该占用单键的主要理由之一。
3. **Esc 是唯一的例外，因为它没有输入语义。** Esc 在文本框、地图、列表里都不承担"输入一个字符"的职责，本来就是"退出/取消"的通用键，且 PRD FR-08 明确要求小木支持 Esc。即便如此，Esc 也有真实的多处消费问题（第 4 节）。
4. **Alt 组合避开浏览器与系统快捷键。** 用 `Ctrl+W`（关标签页）、`Ctrl+R`（刷新）、`Ctrl+M`（部分浏览器静音标签）会直接把页面搞坏，所以统一用 Alt；同时实现显式排除了 `ctrlKey`/`metaKey`，`Ctrl+Alt+W` 这类系统级组合不会被误吃。

## 4. 冲突检查（实际执行结果）

检索方式：在 `src/pages/MumaiDashboard/` 下检索 `addEventListener("keydown"`，再扩展到整个 `src/`；另检索 `onKeyDown/onKeyUp/onKeyPress`（结果为空）与 `快捷键/shortcut/hotkey`（除注释外无实现）。

全仓 `src/` 只有 **4 处** keydown 监听：

| 位置 | 监听内容 | 备注 |
| --- | --- | --- |
| `agent/XiaomuDock.tsx` 第 206 行 | Esc、Alt+W/E/R/M | 本次键控实现，**无条件挂载**（每个已登录页面都在） |
| `agent/VoiceConsole.tsx` 第 518 行 | 仅 Esc（且仅当 `state.open` 为真） | 诊断控制台自己的关闭 |
| `ui.tsx` 第 530 行 | 仅 Esc（`Modal` 打开期间） | 通用弹窗（异常事件详情等）的关闭 |
| `agent/wakeChannel.ts` 第 692 行 | **任意一次** keydown | 只在 URL 带 `?wake=1` 时注册，且 `{ once: true }`，作用是"用户第一次交互时补一次 `start()`"；不是快捷键 |

### 4.1 实际存在的冲突

**冲突 1（真实、影响明确）：Esc 被"小木气泡"和"页面弹窗"同时消费。**

- 场景：页面上打开了 `ui.tsx` 的 `Modal`（例如异常事件详情），同时右下角气泡可见（`agent.open || expanded` 为真）。
- 行为：两个监听都在 `window` 上、都在冒泡阶段、都**不调用 `stopPropagation`**，所以**两个都会执行** —— 一次 Esc 既关掉了页面弹窗，也关掉了小木气泡并停掉播报（若此刻有未确认的高风险操作，还会被按"取消"处理）。
- 触发顺序**不稳定**：`XiaomuDock` 的 effect 依赖 `[agent.open, agent.turns, expanded, close]`，任何一次状态更新都会"移除再添加"监听器，从而把它移到监听队列尾部。所以"谁先谁后"取决于最近一次重渲染时机，不能依赖。
- 用户预期：用户按 Esc 通常只想关**最上面那一层**（弹窗），结果连小木的播报一起停了，甚至取消了一个待确认的操作。
- 建议键位/行为（**未改代码**）：
  - 首选：气泡的 Esc 在"存在模态弹窗"时不消费（判据可用 `document.querySelector('[role="dialog"][aria-modal="true"], .modal-backdrop')` 或弹窗打开时给 `body` 加的 `overflow: hidden`）；
  - 备选：把气泡的"关闭/打断"改绑 `Alt+X`，Esc 只留给弹窗与控制台；
  - 无论哪种，都建议显式声明优先级，而不是依赖监听器注册顺序。

**冲突 2（真实、后果较轻）：控制台打开时 Esc 被两个组件同时消费。**

- 场景：通过小木助手面板「语音」按钮或 COM4 打开全屏控制台，再按 Esc。
- 行为：`VoiceConsole.onKey`（`state.open` 为真）与 `XiaomuDock.onKey`（此时 `agent.open` 为真）**都会跑**，各自调一次自己的 `close()`：
  - `VoiceConsole.close()` 会停播报、停 ASR、`hasPendingConfirm()` 为真时 `resolveConfirm(false)`，再 `closeAgent()`；
  - `XiaomuDock.close()` 会 `speechSynthesis.cancel()`、有 `pendingConfirm` 时再 `resolveConfirm(false)`、`setExpanded(false)`、再 `closeAgent()`。
- 结果：关闭本身是幂等的（`unmountStandalone` 有 `if (!standalone) return` 保护），界面能正常退出；但同一个关闭动作执行了两遍，且**推断**（未实测）在"等待确认时按 Esc"的路径上会先取消再关闭，随后执行器继续往下走并播报一句「好的，这条指令已经取消。」—— 即关掉界面之后仍可能听到一句收尾播报。建议把关闭收敛成"只由最上层消费者处理一次"。

**冲突 3（不是按键冲突，但同屏冲突）：控制台打开时，右下角小木仍在最上层，出现两个确认面。**

- 层级：`.xd` 是 `z-index: 9300`，`.vc-root` 是 `z-index: 90`，所以全屏控制台的遮罩**盖不住**右下角小木。
- 后果：控制台里发起的高风险确认，会同时出现在控制台的确认模态和右下角气泡的确认卡片里；两处都能点、都调同一个 `resolveConfirm`，点哪边都生效（不会重复执行，因为确认是同一个 Promise）。
- 建议：控制台打开时把气泡面板降级或隐藏（或提高 `.vc-root` 层级并让小木只保留形象）。
- 另外同一角落还挤着"打开小木助手面板"的浮标（`right: 16px; bottom: 52px; 52×52px; z-index: 26`），按 CSS 数值会与常驻形象（`right: 24px; bottom: 24px; 76×76px; z-index: 9300`）明显重叠，可能挡住这个入口；**未在浏览器实测**，需视觉验收确认（详见操作手册 7.10）。

**冲突 4（设置自身的小瑕疵，不是与他人的冲突）**

- 未判断 `event.repeat`：长按会连续触发 Alt+W / Alt+E。
- 未判断输入焦点：焦点在小木助手提问框里按 Alt+W，仍会开关常驻唤醒。因为 Alt+字母在输入框里通常没有输入语义，实际影响小；但这与"不在输入时抢键"的初衷不完全一致。
- 未判断输入法组合态：中文输入法组合过程中的 Alt 组合可能被吃掉（未实测，仅记录）。
- 键名用 `event.key.toLowerCase()`：在 Alt 会改变字符的键盘布局上（例如 macOS 的 Option 组合会产生 `∑` 之类的字符），`Alt+W` 可能匹配不到。当前目标平台是 Windows，实际不受影响，但属于可移植性隐患。

### 4.2 明确"没有发现冲突"的部分

- **Alt+W / Alt+E / Alt+R / Alt+M：全仓没有任何其它监听器处理 Alt 组合键**，也不存在与之同名的业务快捷键，因此当前无冲突。
- **没有单键快捷键**（除 Esc）：全仓没有 `onKeyDown` 属性用法，没有"快捷键/shortcut/hotkey"实现，地图与三维页面也没有键盘控制，所以 Alt 组合键目前不会与任何既有快捷键撞车。
- **`?wake=1` 的首次按键 kick**：只在带该参数时注册一次；按 Alt+W 作为"第一次按键"时，两处都会调 `start()`，而 `start()` 自带 `live/starting` 幂等保护，无实际副作用。真正需要注意的是：这个监听是**任意键**都会触发一次——它只在现场测试用 URL 下存在。

## 6. 本轮结论与遗留

- 键位与实现**逐字核对一致**（第 1 节照 `XiaomuDock.tsx` 第 179–208 行抄录，未做任何"应该是这样"的补写）。
- 键位分组合理，且不与任何既有快捷键冲突；**唯一的真实键位冲突是 Esc 的多处消费**（4.1 冲突 1、2）。
- 需要产品/开发决策的三件事（本轮未改代码）：
  1. Esc 的优先级规则（弹窗优先还是气泡优先，或把气泡改绑 `Alt+X`）；
  2. 控制台打开时右下角小木的层级与"双确认面"是否需要收敛；
  3. Alt+W/E/R/M 是否补上 `event.repeat`、输入焦点与输入法组合态判断。
- 另外两个影响"键控能不能用"的实现缺陷（详见操作手册 7.1、7.7，本文件不复述细节）：
  - 产生过回复之后，气泡**关不掉也收不起**，于是 **Esc / Alt+E 的实际观感是"没反应"** —— 这是当前键控最需要先修的前置问题；
  - `Alt+M` 在"推流暂停"期间不会立即恢复聆听（`start()` 在 `live` 时直接返回）。
