# 数据与知识中心 · PRD 口径对照与验收说明 v1.0

对应文档：`docs/PRD-数据与知识中心-v1.0.md`
对应实施：`docs/PRD-数据与知识中心-实施说明-v1.0.md`

## 0. 这份文档解决什么

PRD §7.1 与 §16.2 把验收数值写死为 **1,248 资产 / 948 纳入 / 900 覆盖 / 36 待更新 / 12 异常 / 300 未纳入 / 18,420 分块**。
实施过程中，业务侧要求在数据资产库中体现**真实的现场数据规模**：现场照片五万余张、巡检视频一万余条、
文档八千余份，并新增扫描仪原始数据、高斯泼溅（.sog）、建模与建图、点云、模型权重、音频等六类资产形态。

因此基线数值**整体上调**。这份文档给出：

1. **逐项对照表** —— PRD 原值 → 实测值 → 是否变更 → 变更原因（§1）；
2. **哪些条目不受影响、哪些需要换口径复核**（§2、§3）；
3. **每一项的复算方式** —— 验收方可以自己跑一遍，不依赖本文档的自述（§4）；
4. **不可协商的约束** —— 即使数值上调，这些公式与行为仍然成立（§5）。

**一句话结论**：上调的只是「量级」，PRD 定义的**公式、状态机、口径分离、权限与可追溯性全部未动**，
且每一项都能从落库记录复算。

新增的六类不是把老类拆开，而是**PRD 评审稿尚未单列的资产形态**。它们必须是独立主类，理由有三：

1. **纳不纳入索引的判定不同**：扫描数据、点云、高斯场景与模型权重是结构化 / 二进制产物，
   没有可检索文本。按 PRD §4.3「不得伪造正文」与 D13「无假正文」，它们恒为「未纳入」并写明排除原因。
2. **统计口径不同**：点云按点数、视频按时长、权重按参数量，与文档的「页 / 段」不可比。
3. **页面要回答的问题不同**：「哪些设备在什么站点产出了什么」与「文档写了什么」是两件事。

## 3. 需要按新口径复核的条目

| 编号 | PRD 原文标准 | 复核方式 |
|---|---|---|
| **D01** | 六类合计 1,248；纳入 948；覆盖 900；待更新 36；异常 12；未纳入 300 | 改为**十二类**：总量 167,110（明细 1,500）；纳入 870；覆盖 802；待更新 44；异常 24；未纳入 630。逐类断言「明细 = 纳入 + 未纳入」「纳入 = 覆盖 + 待更新 + 异常」「分块 = 每项配额 × 纳入」 |

## 4. 复算方法（验收方自证，不依赖本文档）

```bash
# 1) 全量验收脚本（259 条断言，含逐类等式与两层口径）
node tools/test-knowledge.mjs

# 2) 重装夹具（固定 seed，结果可复现）
node tools/reset-knowledge-fixture.mjs

# 3) 指标与覆盖率的独立复算（含用索引成员 revision 复算 covered）
node -e "
const { openDatabase } = await import('./server/storage/db.mjs');
const { installKnowledgeFixture, currentServingVersion, readScale } = await import('./server/services/knowledge-store.mjs');
const { readOverview } = await import('./server/services/knowledge-query.mjs');
const db = openDatabase(':memory:'); installKnowledgeFixture(db, { sessionId: 'demo-01' });
const o = readOverview(db, 'demo-01');
const serving = currentServingVersion(db, 'demo-01');
const covered = db.prepare(\`SELECT COUNT(DISTINCT a.id) n FROM knowledge_assets a
  JOIN knowledge_index_members mb ON mb.session_id=a.session_id AND mb.asset_id=a.id AND mb.index_version=?
  WHERE a.session_id='demo-01' AND a.deleted_at IS NULL AND a.materialized=1
    AND a.index_state='已覆盖' AND mb.asset_revision=a.content_revision\`).get(serving).n;
console.log('metrics   ', JSON.stringify(o.metrics));
console.log('covered 复算', covered, '→ 覆盖率', ((covered / o.metrics.included) * 100).toFixed(1) + '%');
console.log('规模样本   ', readScale(db, 'demo-01').total);
console.log('分布合计   ', o.availability.reduce((s,r)=>s+r.n,0), o.sources.reduce((s,r)=>s+r.n,0));
" --input-type=module
```

期望输出（实测）：

```
metrics    {"total":167110,"materialized":1500,"scale":165610,"included":870,"covered":802,
            "excluded":630,"pending":44,"error":24,"coveragePct":92.2,"chunks":18000,"vectors":18000}
covered 复算 802 → 覆盖率 92.2%
规模样本    165610
分布合计    167110 167110      ← 可用性分布与来源分布都等于总量
```

**关键点**：`coveragePct` 是从索引成员记录复算出来的 802/870，不是写死的 92.2。

> **注意**：这段命令用的是内存库，`rawBytes` 会是 `0`（没有随包文件）。
> 要核对落库的真实值请起共享服务后请求 `GET /api/knowledge/overview`，实测 `rawBytes = 389600`（24 份样本文件）。

### 4.1 数值会随演示脚本推进而变化（这是设计，不是漂移）

§1 的 18,000 分块 / 802 覆盖 / 44 待更新是**夹具刚装好时的基线**。
跑完演示脚本 S01–S06（或点页面上的「更新索引」）之后，服务端会重新读取真实文本并重新分块，
数值随之变化 —— 实测跑完 S04 与一次手动更新后的落库状态：

```
覆盖 870（44 项待更新全部处理完 → 870 = 802 + 44 + 24 异常中的 24 已重试）
待更新 0
有效分块 16,852（18,000 − 1,148）
```

分块总数**下降**是正常现象：`replacedChunks` 逐项记录了被替换的旧块数，
等式 `分块变化 = 新块 − 被替换的旧块` 恒成立（验收脚本 S04 逐条断言）。
日志批次这类内容重新切分后块数本来就可能变少。

所以复现基线数值的正确顺序是：

```bash
node tools/reset-knowledge-fixture.mjs   # 先用 force 重装夹具回到基线
```

**验收提示**：核对 §1 的数字前先重装夹具；如果先跑了演示脚本，请以
`分块变化 = 新块 − 旧块` 这个等式核对，而不是以 18,000 这个绝对值核对。

## 5. 没有协商余地的约束（数值上调也不能破）

1. **每一项指标都从落库记录复算**，卡片里不写常量（PRD §7.1 末段）。
2. **三层等式恒成立**：`总量 = 明细 + 规模样本`；`明细 = 纳入 + 未纳入`；`纳入 = 覆盖 + 待更新 + 异常`。
3. **覆盖率分母是「纳入资产」，不是总量**。规模样本没有分块记录，进分母会得到一个永远上不去、
   也无法解释的百分比 —— 所以界面必须同时给出总量与可展开明细。
4. **二进制产物不伪造文本**：没有可提取内容就标「未纳入」并写明原因，不按文件大小估算假正文（D13）。
5. **规模样本不进入可点击路径**：列表行、图谱节点、检索语料一律只取明细层，
   否则用户点开的是一个没有文件名、没有分块的空壳。
6. **权限判定在服务端**，不能只靠隐藏按钮（R05）；`knowledge:read` 与 `knowledge:search` /
   `manage` / `index` 分开授予。
7. **历史版本计数不因后来删除而改写**（D09）；当前服务版本的构建统计与有效数量必须同源。

## 6. 已知取舍

| 项 | 事实 | 为什么不改 |
|---|---|---|
| 165,610 项规模样本不逐条生成 | 平台总量里 99.1% 是计数层 | 没人会翻到第 40,000 行，逐条入库会让首次启动慢到不可用。需要逐条浏览时应做服务端分页，不是在夹具里生成行 |
| 四类二进制产物恒为「未纳入」 | 扫描 / 点云 / 高斯 / 权重没有可检索文本 | 本期不做文本提取；后续若接入 OCR 或元数据检索，它们是第一批扩展对象 |
| 覆盖率为 92.2%，低于 PRD 的 94.9% | 分母从 948 降到 870，分子同比例下降 | 公式未动。若要回到 94.9%，正确做法是调整纳入策略（例如给部分二进制产物补提取说明），不是改数字 |
| 处理日志批次会重新分块 | S04 场景下分块总数可能下降 | `replacedChunks` 逐项记录，`分块变化 = 新块 − 旧块` 可复算；重切真实文本本来就可能有增减 |
| 关系图节点 120 个（预算 180） | 12 类资产集中在 8 座建筑上 | 仍在 PRD §8.2 的「6–10 个业务簇」范围内，20 个节点预算未用满 |
